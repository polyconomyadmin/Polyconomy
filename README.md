# Polyconomy

Polyconomy is an AI assistant for economics. Users ask questions in a chat interface and get answers generated by a retrieval-augmented generation (RAG) service trained on economics research and literature. It was developed in collaboration with the University of Buckingham and the Vinson Centre.

- **Live site:** https://polyconomy-74386831d29f.herokuapp.com/
- **Repository:** https://github.com/polyconomyadmin/Polyconomy
- **Admin inbox:** polyconomy.admin@gmail.com (receives Contact Us messages and upgrade requests)

This document is written for handoff: it should be enough for a new developer to run, change and deploy the project without prior context.

## Features

**Guest chat** (`/`, no account needed)
- Ask up to 5 questions per chat, then a popup asks the user to sign in.
- Answers are revealed word by word, with a Stop button while generating.
- Per-message actions: copy, share, read aloud, try again, edit and resend.
- Automatic translation: the question's language is detected, the question is translated to English for the RAG service, and the answer is translated back.
- A sign-in panel is fixed in the sidebar on desktop; on phones the sidebar is hidden and a Sign In button appears in the header instead.

**Signed-in chat** (`/chat`)
- Everything in the guest chat, with no question limit.
- Chat history saved to the database: create, select, pin/unpin and delete chats.
- Pinned and Chats sections in the sidebar can be collapsed (remembered per browser).
- Export any chat as CSV from its ⋯ menu (columns: `Sender`, `Message`; the automatic greeting is left out).
- User card at the bottom of the sidebar (photo or initials, name, plan) with a menu for Upgrade plan, Profile and Log out.
- On small screens (≤768px) the sidebar starts closed and slides over the chat when opened.

**Accounts**
- Sign up with an account type (Student, Professional or Enterprise). Student accounts require an academic email address (`.edu` / `.ac` / `.ac.xx`).
- Log in with username or email.
- Forgot password: emails a reset link valid for 1 hour.
- Profile page (`/settings`): upload/remove a profile photo, edit name, change password, sign out.
- Upgrade Plan page (`/plans`): Free / Professional / Institute plan cards. There is no billing: Upgrade and Contact Sales open a pre-filled email to the admin inbox.

**Other pages**
- About (`/about`): project description and partner logos (Summerleaze, Buckingham School of Computing, Vinson Centre, IEA).
- Contact Us (`/contact`): form that emails the admin inbox, with reply-to set to the sender.

**Reliability**
- The app checks the backend's health on load and when entering `/chat`, and shows a maintenance popup if the server, database or AI service is down (see [Health checks and outage popups](#health-checks-and-outage-popups)).

## Architecture

```
                      ┌──────────────────────────────────────────────┐
  Browser             │  Heroku web dyno (one Django app)            │
  ───────             │                                              │
  Angular app  ──────▶│  /api/...        Django REST endpoints       │──▶ MongoDB Atlas
  (served by Django   │  /static/...     Built Angular files         │    (users, chats,
   from the same      │                  (WhiteNoise)                │     RAG query tasks)
   Heroku app)        │  everything else Angular index.html          │
                      │                                              │──▶ RAG service
                      │  Background thread per question ─────────────┼──▶ (external, via
                      │                                              │    RAG_SERVICE_URL)
                      │  Emails (password reset, contact) ───────────┼──▶ Brevo SMTP
                      └──────────────────────────────────────────────┘
  Browser also calls translate.googleapis.com directly for language detection/translation.
```

Key points:
- **One deployable.** The Angular frontend is built locally and the output is **committed into `backend/`**. Heroku only runs Django, which serves both the API and the built frontend. See [Building and deploying](#building-and-deploying).
- **MongoDB via MongoEngine**, not the Django ORM. Django's own database is set to a dummy backend, so Django admin, sessions and `migrate` do nothing useful.
- **The AI is a separate service** (not in this repo), reached over HTTP at `RAG_SERVICE_URL`. Questions are processed asynchronously: the browser submits a question, gets a task ID, and polls for the answer.

## Running locally

### Prerequisites
- Node.js 20+ (developed on Node 23) and npm
- Python 3.12

### Frontend only (most UI work)

```bash
cd frontend
npm install
npm start          # ng serve on http://localhost:4200
```

> **Important:** the API base URL is hard-coded to the **production** Heroku backend in `auth.service.ts`, `rag.service.ts`, `health.service.ts` and `pages/chat/chat.component.ts`. Running the frontend locally therefore talks to the live backend and the live database. Signing in locally uses real accounts and creates real chats. To develop against a local backend, change those URLs (ideally move them into one `environment` file first).

Known local-dev quirks:
- Images referenced as `/static/frontend/assets/...` don't load under `ng serve` (the dev server serves them at `/assets/...`). They work in production.
- The outage popup will show "Server Unavailable" if the live backend is down or doesn't yet have `/api/health/`.

### Backend

```bash
cd backend
python3 -m venv .venv && source .venv/bin/activate
pip install -r ../requirements.txt     # root file: includes PyJWT, which backend/requirements.txt lacks
export MONGO_URI="mongodb+srv://..."    # a development database, ideally not production
export RAG_SERVICE_URL="https://..."    # optional; chat answers fail without it
export RAG_API_KEY="..."
python manage.py runserver 8000
```

Then open http://localhost:8000 to use the committed frontend build, or point the frontend's API URLs at `http://localhost:8000/api` and use `ng serve`.

There is no automated test suite for the backend. Endpoints have been verified with Django's test client (`django.test.Client`) with `mongoengine` lookups mocked, so tests don't touch the real database.

## Building and deploying

Heroku deploys from the `main` branch of the GitHub repo. **Heroku does not build the Angular app**: the root `package.json` has no `build` script, so the Node.js buildpack only installs packages. The built frontend must be committed.

### After any frontend change

```bash
cd frontend
rm -rf dist && npx ng build            # outputs to frontend/dist/frontend
cd ..
D=frontend/dist/frontend
rm -rf backend/frontend && cp -R $D backend/frontend
for t in static staticfiles templates; do
  rm -rf backend/$t/frontend && cp -R $D/browser backend/$t/frontend
done
git add frontend/src backend
git commit -m "..."
git push                                # Heroku deploys main
```

Why four copies: Django serves `templates/frontend/index.html` for every non-API URL, and serves JS/CSS/assets from `/static/frontend/` (collected into `staticfiles/` and served by WhiteNoise). The file names contain content hashes (e.g. `main-LP7CDGXV.js`), so each build replaces the old files. By convention the project commits source changes and the rebuilt files as two separate commits ("Rebuild frontend static files").

The root `package.json` script `build-frontend` is out of date (it copies to the wrong place); use the steps above.

The build prints CSS "budget" warnings and a few `document is not defined` / `localStorage is not defined` prerender errors. Both are harmless and existed before these notes were written.

### Backend-only changes
Just commit and push. Heroku installs `requirements.txt` (root) and runs the root `Procfile`:

```
web: PYTHONPATH=backend gunicorn config.wsgi:application
```

This uses Gunicorn's default 30-second timeout. That's fine because RAG questions run in a background thread (see below). The `--timeout 150` in `backend/Procfile` is not used.

### Checking a deploy
- `curl https://polyconomy-74386831d29f.herokuapp.com/api/health/` should return `{"status": "ok", "database": "ok", "rag": "ok"}`.
- Compare the `main-*.js` file name in the live page source with `backend/templates/frontend/`.

## Environment variables

Set these as Heroku config vars (*Heroku dashboard → app → Settings → Config Vars*).

| Variable | Required | Purpose |
|---|---|---|
| `MONGO_URI` | Yes | MongoDB Atlas connection string |
| `RAG_SERVICE_URL` | Yes | Base URL of the RAG service (the app calls `<url>/query`) |
| `RAG_API_KEY` | Yes | Sent to the RAG service in the `x-api-key` header |
| `BREVO_SMTP_LOGIN` | Yes (for email) | Brevo SMTP login (looks like `xxxxxx@smtp-brevo.com`) |
| `BREVO_SMTP_KEY` | Yes (for email) | Brevo **SMTP key** (not an API key) |
| `DEFAULT_FROM_EMAIL` | No | Sender address; default `Polyconomy <polyconomy.admin@gmail.com>`. Must be a verified sender in Brevo |
| `CONTACT_EMAIL` | No | Where Contact Us messages go; default `polyconomy.admin@gmail.com` |
| `EMAIL_HOST` / `EMAIL_PORT` | No | Override the SMTP server; default `smtp-relay.brevo.com` / `587` |
| `DEBUG` | No | Read in settings to decide whether to warn about missing RAG config |

Variables referenced only by the unused `rag-gemini.py` / `rag-antrophic.py` experiments (`GEMINI_API_KEY`, `ANTHROPIC_API_KEY`) and older `DB_*` variables are not needed.

`FRONTEND_URL` (used to build password-reset links) is set directly in `settings.py`; update it if the domain changes.

### Routes (`app.routes.ts`)

| Path | Component | Access |
|---|---|---|
| `/` | `GuestChatComponent` | Public |
| `/login`, `/signup`, `/select-plan`, `/reset-password` | `LandingComponent` (one component, several steps) | Public |
| `/chat` | `ChatComponent` | Signed in |
| `/settings` | `AccountSettingsComponent` (Profile) | Signed in |
| `/plans` | `PlansComponent` (Upgrade Plan) | Signed in |
| `/about` | `AboutComponent` | Public |
| `/contact` | `ContactComponent` | Public |
| anything else | redirects to `/` | |

"Signed in" means a token exists in `localStorage` (`auth.guard.ts`). The About/Contact back buttons return signed-in users to `/chat` and guests to `/`.

### Browser storage (`localStorage`)

| Key | Contents |
|---|---|
| `token` | Login JWT (24-hour expiry) |
| `user` | `{ username, email, name, plan, avatar }` from login/profile responses |
| `sidebarCollapsed` | `{ pinned, chats }` collapsed state of the chat sidebar sections |

Logging out clears all of `localStorage`.

### Styling
- Design tokens (colours, radii, fonts) live in `src/styles.css` as HSL triplets, used as `hsl(var(--primary))`. A `.dark` class set exists but isn't switched on anywhere.
- Most page CSS is component-scoped. Global rules worth knowing: `body` has `overflow: hidden` (the chat layout needs it), so full pages (`.page` in About/Contact/Profile/Plans) scroll themselves. `lucide-icon svg { display: block }` keeps icons vertically centred.
- The app is **zoneless** (Angular 21 default). After async work outside Angular's own events (timers, HTTP callbacks that mutate plain fields), call `ChangeDetectorRef.markForCheck()` or use signals, otherwise the view won't update.

### Plans and account types
`user.plan` stores the **account type** chosen at sign-up (`student`, `professional`, `enterprise`), not a paid tier. There is no billing, so everyone is shown as being on the **Free** plan. Upgrading is handled by email: the Upgrade and Contact Sales buttons open a pre-filled email to the admin inbox.

## Backend API

All endpoints are under the same host as the site. JSON in, JSON out.

### Auth and account — `/api/users/`

| Method | Path | Body | Notes |
|---|---|---|---|
| POST | `signup/` | `email, password, username, name, plan` | Returns `{ token, user }` |
| POST | `login/` | `identifier` (username or email), `password` | Returns `{ token, user }` |
| POST | `forgot-password/` | `email` | Always returns success (doesn't reveal whether the email exists). Emails a link to `/reset-password?uid=…&token=…`, valid 1 hour |
| POST | `reset-password/` | `uid, token, password` (8+ chars) | |
| POST | `profile/` | `name` and/or `avatar` (a `data:image/jpeg\|png\|webp;base64,…` URL up to ~300 KB, or `null` to remove) | **Requires** `Authorization: Bearer <token>`. Returns `{ user }` |
| POST | `change-password/` | `current_password, new_password` (8+ chars, different) | **Requires** `Authorization: Bearer <token>` |
| POST | `contact/` | `name, email, subject, message` | Emails `CONTACT_EMAIL` with reply-to set to the sender. `502` if sending fails |

### Chats — `/api/users/chats/<username>/`

| Method | Path | Body | Returns |
|---|---|---|---|
| GET | `` | | `{ chats: [{ chat_id, title, pinned, messages: [{ text, sender }] }] }` |
| POST | `new/` | optional `title` | `{ chat_id, title }` |
| POST | `<chat_id>/add/` | `text, sender` (`user` or `ai`) | |
| POST | `<chat_id>/pin/` | `pinned` | |
| DELETE | `<chat_id>/delete/` | | |

The signed-in chat saves a question only once its answer arrives (or when the user presses Stop), so a failed question can be returned to the input box without leaving a trace in history.

### Questions (RAG) — `/api/query/`

| Method | Path | Body | Returns |
|---|---|---|---|
| POST | `/api/query/` | `question` | `{ task_id, status: "pending" }` immediately |
| GET | `/api/query/<task_id>/status/` | | `{ task_id, status: "pending"\|"done"\|"error", answer, sources, timings }` |

### Health — `/api/health/`

`GET` returns `200 {"status":"ok","database":"ok","rag":"ok"}` or `503` with `"database": "down"` and/or `"rag": "down"`. The database check is a MongoDB ping (5s timeout); the RAG check is a GET to `RAG_SERVICE_URL` (5s timeout) where connection errors, 502/503/504, or an ngrok "endpoint offline" response count as down.

### Login tokens
`create_jwt` in `jwt_utils.py` issues an HS256 JWT (signed with Django's `SECRET_KEY`) containing `user_id`, `username` and `name`, valid for 24 hours. `get_user_from_request` verifies the `Authorization: Bearer` header and returns the user, or `None`. Currently only `profile/` and `change-password/` use it (see [Known issues](#known-issues-and-gotchas)).

## Data model

MongoEngine documents in `backend/apps/users/models.py`:

**`User`** (collection `users`)
- `username` (unique), `email` (unique), `name`
- `password_hash` (Werkzeug hash; use `set_password` / `check_password`)
- `plan`: account type, one of `student`, `professional`, `enterprise`
- `avatar`: profile photo as a data URL (256×256 JPEG, resized in the browser) or `null`
- `is_admin`, `created_at`
- `reset_token`, `reset_token_expiry`: password-reset state
- `chats`: list of embedded **`Chat`** (`chat_id`, `title`, `pinned`, `created_at`, `messages`)
  - each **`Message`**: `text`, `sender` (`user` | `ai`), `timestamp`

Chats are embedded in the user document, so a very heavy user's document grows with their history. MongoDB's 16 MB document limit is the long-term ceiling.

**`RagQuery`** (collection `rag_queries`): one per question, used for polling
- `id` (UUID), `question`, `status` (`pending` | `done` | `error`), `answer`, `sources`, `timings`, `created_at`, `updated_at`

Old `RagQuery` documents are never deleted.

## How a question is answered (RAG flow)

1. **Browser:** the chat component detects the question's language with `translate.googleapis.com` and gets an English version.
2. **Browser → Django:** `POST /api/query/` with the English question. Django creates a `RagQuery` (`pending`), starts a **background thread**, and returns the `task_id` straight away (Heroku's router kills requests after 30 s, and answers can take minutes).
3. **Django → RAG service:** the thread calls `POST {RAG_SERVICE_URL}/query` with `{"question": ...}` and headers `x-api-key: RAG_API_KEY` and `ngrok-skip-browser-warning: true`. It retries connection failures 3 times, then waits indefinitely for the response. The service must return JSON `{ answer, sources, timings }`.
4. **Django:** the thread stores the result. Any answer starting with `Error` marks the task `error`.
5. **Browser:** polls `GET /api/query/<task_id>/status/` every 3 s, gives up after 5 minutes, then translates the answer back to the user's language and reveals it word by word.

The background thread lives inside the web dyno. If the dyno restarts mid-question, that task stays `pending` forever; the browser's 5-minute limit covers this.

The RAG service itself is **not in this repository**. It has been hosted from a notebook exposed through ngrok, so its URL changes whenever the tunnel restarts; update `RAG_SERVICE_URL` in Heroku when that happens.

## Health checks and outage popups

`HealthService` (`frontend/src/app/services/health.service.ts`) calls `/api/health/` on load and whenever the user enters `/chat`. The root component shows one of three popups (styled like the site's other modals, with Close and Try Again):

| Popup | When |
|---|---|
| **Server Unavailable** | The backend can't be reached at all |
| **Database Unavailable** | Backend up, MongoDB down (shown on load) |
| **Polyconomy AI Unavailable** | RAG service down. **Not** shown on load; shown when the user tries to send a message |

When the AI is known to be down, sending does nothing except show the popup; the text stays in the input. If a question fails partway through, it is pulled back out of the chat into the input box and the popup appears.

## Email

Django's SMTP backend sends through **Brevo** (`smtp-relay.brevo.com:587`, STARTTLS), configured in `backend/config/settings.py` from the environment variables above. Two things send email:
- **Password reset** (`forgot_password` in `views.py`)
- **Contact Us** (`contact_message` in `views.py`)

Both send during the request, with a 15-second SMTP timeout. Failures are logged; password-reset failures are hidden from the user by design.

To set up or move the Brevo account:
1. Create a Brevo account (the free plan allows 300 emails/day).
2. Under *Senders, Domains & Dedicated IPs → Senders*, verify the From address (`polyconomy.admin@gmail.com`).
3. Under *SMTP & API → SMTP*, copy the SMTP login and generate an SMTP key.
4. Set `BREVO_SMTP_LOGIN` and `BREVO_SMTP_KEY` in Heroku.

Upgrade requests don't go through the server: the Upgrade Plan page opens a `mailto:` link in the user's own email app.

## Known issues and gotchas

- **Chat endpoints don't check the login token.** `/api/users/chats/<username>/…` trusts the username in the URL, so anyone who knows a username can read or change that user's chats. The fix is to require `get_user_from_request` on each chat endpoint and send the `Authorization` header from `chat.component.ts`.
- **API base URL is hard-coded** to production in four frontend files (see [Running locally](#running-locally)).
- **The frontend must be rebuilt and committed by hand**; forgetting means the live site doesn't change.
- **Django admin (`/admin/`) doesn't work** because Django's database is a dummy backend.
- **`backend/requirements.txt` is missing PyJWT**; install from the root `requirements.txt`.
- **Two Procfiles and two runtime files:** Heroku uses the root ones (`Procfile`, `runtime.txt` = Python 3.12.8).
- **`rag.py` waits forever** for the RAG service once connected; the frontend's 5-minute limit is the only cap.
- **Old `RagQuery` documents accumulate**; consider a TTL index on `created_at`.
- **Unused files:** `backend/apps/users/rag-*.py`, `backend/apps/users/papers/`, and the commented-out Google sign-in code in `backend/api/views.py`.
- **Plans aren't real tiers yet:** see [Plans and account types](#plans-and-account-types). Adding paid plans needs a new field on `User` (e.g. `subscription`) and a billing integration.
